================================================================================
                    AI CASCADE ROUTER — КАК ЭТО РАБОТАЕТ
================================================================================

Этот документ объясняет логику работы ядра роутера простым языком.

--------------------------------------------------------------------------------
                            ОСНОВНАЯ ИДЕЯ
--------------------------------------------------------------------------------

Большинство запросов к LLM — простые. Их можно обработать бесплатной локальной
моделью. Сложные запросы — отправить в платное облако.

РОУТЕР = "привратник", который решает куда направить каждый запрос.

================================================================================
                          ЭТАПЫ ОБРАБОТКИ ЗАПРОСА
================================================================================

Пользователь отправляет запрос: "Привет! Напиши функцию на Python для факториала"

Этап 1. КЛАССИФИКАЦИЯ
----------------------
Роутер анализирует запрос и определяет:

  а) ДОМЕН (тип задачи):
     • code      → генерация кода
     • analysis  → анализ данных
     • chat      → простой чат
     • question  → вопросы
     • creative  → креативное письмо
     • technical → технические задачи

  б) СЛОЖНОСТЬ:
     • Простая   → короткий запрос, нет сложных слов
     • Средняя   → есть ключевые слова (анализ, код, создай...)
     • Сложная   → многоступенчатый запрос

  в) MULTI-STEP? (многоступенчатый?):
     • Есть слова "и", "затем", "также", "потом" → ДА
     • Запрос разбивается на подзадачи


Этап 2. ВЫБОР ПОРОГА УВЕРЕННОСТИ
--------------------------------
Для каждого домена — свой порог. Это настраивается в config.yaml:

  Код (code)        → порог 0.65 (ниже = чаще локально)
  Анализ (analysis) → порог 0.80 (выше = чаще в облако)
  Чат (chat)        → порог 0.60 (очень низкий = почти всегда локально)
  Вопрос (question) → порог 0.55 (минимум = локально)
  Креатив (creative)→ порог 0.70 (средний)
  Техническое      → порог 0.75 (выше среднего)

ПОРОГ = число от 0 до 1. Это "уверенность", при которой запрос идёт локально.


Этап 3. СЕМАНТИЧЕСКИЙ КЭШ (ПРОВЕРКА КЭША)
-----------------------------------------
Перед отправкой на модель:

  1) Проверяем точный хэш запроса
  2) Если нет → ищем семантически похожий (эмбеддинги)
  3) Cosine similarity > 0.8 → возвращаем сохранённый ответ БЕЗ обращения к модели

Это экономит время и токены.


Этап 4. ОБРАБОТКА ЗАПРОСА
-------------------------

ВЫБОР МАРШРУТА:

  ┌─────────────────────────────────────────────────────────────┐
  │                    РЕЗУЛЬТАТ: LOCAL                          │
  │  Запрос → Локальная модель (LM Studio) → Ответ             │
  │                                                             │
  │  Модель делает Self-Assessment:                            │
  │  • Считает свою уверенность (0.0 - 1.0)                    │
  │  • Определяет флаги ("неизвестный термин",                 │
  │    "недостаточно контекста", "требует фактчекинг")          │
  │                                                             │
  │  ЭКОНОМИЯ = все токены локальной модели                    │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │                    РЕЗУЛЬТАТ: HYBRID                        │
  │  Запрос → Локальная модель (извлечение контекста) →        │
  │        → Облачная модель (финальный ответ)                 │
  │                                                             │
  │  Локальная модель提取 ключевую информацию                  │
  │  Облачная использует этот контекст                          │
  │                                                             │
  │  ЭКОНОМИЯ = токены локального preprocessing                │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │                    РЕЗУЛЬТАТ: CLOUD                          │
  │  Запрос → Облачная модель (GPT-4o-mini, Llama, Gemma...)   │
  │                                                             │
  │  Используется для сложных запросов или когда               │
  │  локальная модель дала низкую уверенность                  │
  │                                                             │
  │  ЭКОНОМИЯ = 0 (платим облаку)                              │
  └─────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────┐
  │                    РЕЗУЛЬТАТ: CASCADE                        │
  │  Для многоступенчатых запросов:                             │
  │                                                             │
  │  "Проанализируй данные и создай отчёт с графиками"          │
  │                                                             │
  │  Декомпозиция:                                              │
  │  1) "Проанализируй данные"     → LOCAL                      │
  │  2) "Создай отчёт"            → CLOUD                      │
  │  3) "Добавь графики"          → HYBRID                      │
  │                                                             │
  │  Каждая подзадача обрабатывается отдельно                  │
  │  ЭКОНОМИЯ = сумма токенов всех local/hybrid подзадач       │
  └─────────────────────────────────────────────────────────────┘


Этап 5. ОБРАБОТКА ОШИБОК (FALLBACK)
-----------------------------------

  а) Локальная модель недоступна:
     → Retry 3 раза с экспоненциальной задержкой (1с, 2с, 4с)
     → Если всё равно не работает → автоматический переход в облако

  б) Облачная модель возвращает 404 (модель недоступна):
     → Пробует следующую модель из списка free_models
     → Перебирает все доступные модели
     → Если ничего не работает → ошибка


Этап 6. ЗАПИСЬ МЕТРИК
----------------------

После каждого запроса записываем:

  • total_requests      — всего запросов
  • local_requests     — обработано локально
  • cloud_requests     — обработано в облаке
  • tokens_saved        — сэкономленные токены
  • total_cost_usd      — потраченные деньги
  • avg_response_time  — среднее время ответа
  • delegation_rate     — доля запросов в облако
  • roi_percent         — ROI в процентах

================================================================================
                            ПРИМЕР РАБОТЫ
================================================================================

Запрос: "Напиши функцию вычисления факториала на Python"

1. Классификация:
   → Домен: code (есть слово "функция", "напиши")
   → Сложность: средняя (есть ключевое слово "код")
   → Multi-step: НЕТ

2. Выбор порога:
   → Для code порог = 0.65
   → Порог ниже среднего → запрос скорее всего пойдёт локально

3. Проверка кэша:
   → Похожих запросов нет → идём дальше

4. Обработка:
   → Выбран маршрут: LOCAL
   → LM Studio генерирует код
   → Self-assessment: "Уверенность 0.82, флаги: []"
   → Уверенность 0.82 > порога 0.65 → ОК, возвращаем ответ

5. Метрики:
   → tokens_saved = 45 (сколько токенов ушло на локальную модель)
   → source = "local"

================================================================================
                         КОНФИГУРАЦИЯ ПОРОГОВ
================================================================================

В файле config.yaml настраивается:

  routing:
    domain_thresholds:
      code: 0.65        # Код — чаще локально
      analysis: 0.80    # Анализ — чаще в облако
      chat: 0.60        # Чат — почти всегда локально
      question: 0.55    # Вопросы — локально
      creative: 0.70    # Креатив — средний
      technical: 0.75   # Техническое — выше среднего

Чем НИЖЕ порог → чаще запрос идёт локально (больше экономия)
Чем ВЫШЕ порог → чаще запрос идёт в облако (выше качество)

================================================================================
                              ПЛЮСЫ ПОДХОДА
================================================================================

1. ЭКОНОМИЯ 40-70% — простые запросы обрабатываются бесплатно
2. КАЧЕСТВО — сложные запросы идут в мощные облачные модели
3. СКОРОСТЬ — local модели отвечают быстрее облачных
4. НАДЁЖНОСТЬ — есть fallback при ошибках
5. КЭШ — семантический поиск повторяющихся запросов
6.ГИБКОСТЬ — настраиваемые пороги под разные задачи
