================================================================================
  AI Cascade Router v2 — концепция мульти-провайдерного роутера для продакшена
================================================================================

Основана на текущем коде AI Cascade Router (v0.7).
Цель: сохранить идею умной маршрутизации, но сделать её готовой к тысяч/миллионам
пользователей.

--------------------------------------------------------------------------------
 1. Проблемы текущей архитектуры
--------------------------------------------------------------------------------

1.1. Жёсткая привязка к LM Studio
  - Если LM Studio не запущена — проект бесполезен
  - local model = один инстанс на весь сервер
  - Нет graceful degradation (падаем с ошибкой вместо fallback)

1.2. Нет мульти-провайдерности
  - Cloud только OpenRouter
  - Нет failover между провайдерами
  - Нет A/B сравнения стоимости/качества

1.3. max_tokens хардкодом
  - 2000 в local_engine.py, 2000 в cloud/client.py
  - Клиент (Cursor/Continue) шлёт свой max_tokens — мы его игнорируем
  - Нет возможности сказать "дай сколько надо, я подожду"

1.4. Cascade дробит разумные запросы
  - "with", "и" всё ещё могут триггернуть декомпозицию
  - Нет проверки: "а нужна ли вообще декомпозиция?"

1.5. Нет метрик качества
  - Не знаем, сколько раз heuristic ошибся (отправил в cloud, хотя local ответил бы норм)
  - Не знаем latency per provider
  - Не знаем cost per query реальный

 3. Provider tiers
--------------------------------------------------------------------------------

LOCAL (tier 0):  бесплатно, но медленно
  - LM Studio / Ollama / llama.cpp / LocalAI
  - Модели: Qwen 2.5 7B, Llama 3 8B, Mistral 7B, Phi-3
  - Время: ~30-180s на ответ
  - Использовать для: chat, question, простой код

CHEAP (tier 1):  $0.07-0.30/M tok
  - OpenRouter: DeepSeek, Gemini Flash, GPT-4o-mini
  - Время: ~5-15s
  - Использовать для: medium complexity, analysis

PREMIUM (tier 2):  $3-15/M tok
  - OpenAI: GPT-4o, o1, o3
  - Anthropic: Claude Opus, Sonnet
  - Google: Gemini Pro/Ultra
  - Время: ~10-30s
  - Использовать для: complex analysis, strategy, refactoring

Failover: если tier упал → пробуем следующий (local → cheap → premium)

--------------------------------------------------------------------------------
 4. Умный роутинг с Cost-Awareness
--------------------------------------------------------------------------------

Вместо жёстких thresholds — динамический выбор:

Если локальная модель доступна И confidence >= threshold:
  → LOCAL (0$)

Если local недоступна ИЛИ confidence < threshold:
  → Оцениваем стоимость у cheap vs premium
  → Если cheap хватает (ML сказал MEDIUM) → cheap
  → Если cheap не хватит (ML сказал COMPLEX) → premium
  → Если cheap стоит как premium (разница < 20%) → premium (качество)

Это позволяет:
  - Экономить на простых запросах (local или cheap)
  - Не экономить на сложных (сразу premium, без double-spend)
  - Прозрачная статистика: "сегодня сэкономили $X, потратили $Y"

--------------------------------------------------------------------------------
 5. max_tokens и таймауты (решение нашей проблемы)
--------------------------------------------------------------------------------

Принцип: не ограничиваем модель, ограничиваем только время.

5.1. Принимаем max_tokens от клиента
  /v1/chat/completions: request.max_tokens → передаём провайдеру
  CLI: config.yaml → default_max_tokens: 8192

5.2. Таймауты динамические
  LOCAL: 300s (модель медленная)
  CHEAP: 60s
  PREMIUM: 120s
  CLI: 300s

5.3. Если модель не уложилась в таймаут
  → логируем как "timeout"
  → не падаем с ошибкой, а возвращаем то, что успели сгенерировать
  → (требует streaming)

--------------------------------------------------------------------------------
 6. Улучшения для текущего проекта (без переписывания)
--------------------------------------------------------------------------------

Сделать прямо сейчас в текущем коде:

1. max_tokens брать из запроса, хардкод заменить на request.max_tokens
   → /v1/chat/completions уже принимает max_tokens — просто передать в generate
   → local_engine.py: generate(max_tokens=2000) → generate(max_tokens=Optional[int])
   → cloud/client.py: то же самое

2. Таймауты:
   → LocalEngine: timeout из конфига (сейчас 120, норм)
   → CloudClient: timeout из конфига (сейчас 30 хардкод)
   → CLI: убрать хардкод 120, читать из конфига

3. Streaming:
   → Уже есть в /v1/chat/completions
   → Добавить в /route (возвращать stream при stream=True)

4. Cascade: добавить проверку "а нужно ли?"
   → Если после декомпозиции все подзадачи одного типа (все local, все cloud)
     → Consolidate (уже есть для cloud, добавить для local)
   → Не дробить, если subtask < 2 (уже есть)

5. Provider abstraction layer
   → Каждый провайдер реализует интерфейс:
     generate(), generate_stream(), health_check(), cost_per_token()
   → Router Engine выбирает по cost + confidence + latency

--------------------------------------------------------------------------------
 7. Заключение
--------------------------------------------------------------------------------

Текущий проект (v0.7) — отличная proof-of-concept база.
Для миллионов пользователей нужно:
  1. Мульти-провайдерность (не только OpenRouter)
  2. Streaming как обязательный режим
  3. Cost-aware routing (не только threshold-based)
  4. max_tokens от клиента (не хардкод)
  5. Graceful degradation (не падать, а пробовать другой провайдер)

Но твой тезис про локальные модели верен. С каждым годом они:
  - Становятся умнее (Qwen 2.5 → Qwen 3 → ...)
  - Требуют меньше VRAM (4-bit, 3-bit quantization)
  - Работают быстрее (llama.cpp оптимизации)

Поэтому стратегия "local — дёшево и медленно, cloud — дорого и быстро" 
будет только актуальнее.
